# مراجعة المنزل وToday وخطة التعاون

التاريخ: 2026-11-07. الحالة: **مقترح للنقاش قبل التنفيذ**.

هذه مراجعة مستقلة للكود الحالي وmetadata مشروع LifeOS السحابي، مكملة لمسودة [الخطة التفصيلية](home-today-roadmap.md) الموجودة مسبقًا. لم يتغير كود التطبيق أو مخطط قاعدة البيانات، ولم تُقرأ سجلات المستخدمين. لا تمثل هذه الوثيقة اعتمادًا لترحيل أو اختبارًا فعليًا للموبايل أو للمشاركة.

## النتيجة الأساسية

مساحة المنزل مكان لحفظ شؤون البيت ومساعدتنا في قرار مناسب الآن؛ Today خطة كل شخص عبر المساحات. حفظ فكرة، أو شراء مؤجل، أو مشروع لا يعني إدراجه ضمن التزامات اليوم. يمكن توزيع واجهات المساحات بالتوازي بعد الاتفاق على العقود المشتركة، مع مسار منسق واحد لتغيير البيانات والمزامنة والصلاحيات.

الأعمدة السحابية المقروءة تتفق مع life_tasks / projects / day_plans / recipes / inventory_items. لم تظهر جداول households / household_members / shopping_lists / shopping_items / meal_plan_entries / meal_cook_logs في الاستعلام المستهدف. سياسات الجداول المعنية تعتمد user_id. دالتا المزامنة العامتان تفوضان العمل لدوال lifeos_internal التي ما زالت تسحب بحسب المستخدم وتقفل بحسب المستخدم؛ إضافة سياسة قراءة مشتركة وحدها لن تكمل المشاركة.

### نقاط تصحيح قبل توسيع الواجهة

1. `HomeOverview.tsx:118`: وجبة اليوم في localStorage بمفتاح التاريخ فقط، خارج عزل الحساب ودون مزامنة. عبارة اعتماد وجبة «للأسرة» تتجاوز السلوك الحالي؛ ننقلها لاحقًا لخطة وجبات ذات نطاق واضح، ولا نعتبر البيانات القديمة مشتركة تلقائيًا.
2. `HomeOverview.tsx:314`: نقل المقادير يضيف مكونات الوصفة دون خصم الموجود؛ فحص التكرار نصي. الواجهة الحالية لا تحقق «اشترِ الناقص فقط».
3. `homeTasks.ts:3`: الرمز 🛒 وكلمات الوصف تميز الشراء، وكلمات العنوان تميز الصيانة. نستبدلها تدريجيًا بتصنيف وعلاقات منظمة، مع مراجعة العناصر القديمة بدل تخمينها ثم حذفها.
4. `todayAggregator.ts:600` و`projectQueries.ts:158`: «المشروع النشط» حاليًا أي مشروع غير مكتمل؛ فيدخل backlog وwaiting إن كانت له خطوة تالية. لا يكفي تغيير شكل كارت المشروع لإصلاح ذلك.
5. `todayAggregator.ts:631`: مهام المنزل غير المؤرخة تدخل التجميع؛ محرك القرار الموجود يفصل بعض الأساسيات ويقترح عملًا، لكن الأجندة نفسها تظل تعرض التجميع الواسع. المشتريات ليست مستبعدة منه بتصنيف مستقل.
6. `spaceTaskService.ts:62`: revealInToday يفعّل مساحة وتفضيلاتها، وليس تسجيل اختيار شخصي لهذه المهمة فقط. إلغاء هذا الخيار ليس أمر «أزل هذه المهمة من اليوم».
7. `types/tasks.ts:77`: day_plans يحفظ essentialTaskIds مع السعة والنهاية؛ لا يمثل قائمة يوم عامة متعددة المصادر ومرتبة.

## قرارات المنتج المقترحة

### أعمال المنزل

نفصل نوع العنصر عن حالته وتصنيفه ومدته. «سريع» فلتر مدة معروفة، و«صيانة» تصنيف؛ كلاهما يمكن أن ينطبق على مهمة. المشروع مجموعة خطوات، والروتين مصدر تكرار. لا نجبر المستخدم على تقدير مدة أو تحديد تاريخ عند حفظ الفكرة.

| المثال | تمثيله المبدئي | متى يظهر للتنفيذ؟ |
|---|---|---|
| أكوي قميصي | مهمة، خاصة افتراضيًا | عند الاختيار لليوم أو الترشيح حسب الوقت |
| ترويق ومسح الشقة | مهمة منفردة أو روتين حسب اختيار المستخدم | حدوث الروتين المستحق أو الاختيار اليدوي |
| أعدل المكتب | مهمة تحتاج جلسة؛ مشروع فقط لو لها خطوات فعلية | عندما تتاح وتناسب الوقت والسياق |
| تركيب شفاط | مهمة إن كانت خطوة واحدة، أو مشروع قياس/اختيار/شراء/تركيب | الخطوة الجاهزة فقط؛ الشراء مرتبط بقائمة المشتريات |
| شراء سجاد | فكرة في لاحقًا، أو بند شراء عندما يصبح قرارًا | مراجعة اختيارية، ثم مشوار شراء عند الجاهزية |
| تجديد الركنة | مشروع مؤجل أو جارٍ | مراجعة المشروع، ثم اختيار الخطوة التالية |
| انتظار الكهربائي | انتظار مع متابعة اختيارية | موعد المتابعة؛ لا يقترح كعمل جاهز قبلها |

عدم وجود موعد لا يعني التأخر. موعد المراجعة يعيد الفكرة للانتباه، ولا يتحول إلى deadline أو مهمة يوم إلزامية. نقترح مراجعة أسبوعية قصيرة للمؤجل والمشاريع بدل توزيع كل الأفكار على أيام مصطنعة.

### Today

- ثلاث مجموعات واضحة: مختار ليومي، مواعيد وروتين مستحق، واقتراحات محدودة منفصلة (٣ كبداية).
- التقدم اليومي يقاس بخطة اليوم المحددة، ولا يعاقب حفظ أفكار أو عدم قبول اقتراح.
- «أضف ليومي» من المساحة يضيف مرجعًا شخصيًا؛ «أزل من يومي» يحذف الاختيار فقط. الموعد الثابت يظل واضحًا ولا يختفي بسبب إزالة الاختيار.
- من Today يوجد «مهمة جديدة» و«اختيار من المساحات»؛ الثاني يبحث في الأعمال المسموح بها ويصفي حسب المساحة والمدة والسياق.
- إنجاز العنصر يتم في مصدره مرة واحدة. اختيار خطوة مشروع يحتفظ بهويتها، ولا يتحول تلقائيًا إلى الخطوة التالية بعد الإنجاز.
- حدوث الروتين له هوية مرتبطة بالمصدر وتاريخ الحدوث. قائمة مشتريات تدخل اليوم كمشوار أو مهمة مراجعة قائمة، لا كل صنف كمهمة.
- ترتيب يوم الشخص واختياراته لا تنتقل لخطة الزوج/الزوجة. إنجاز عمل مشترك ينعكس لدى الطرفين؛ الاشتراك لا يجعل كل عمل التزامًا على الجميع.

### الأكل والمخزون والشراء

- الوصفة المحفوظة، وخطة الوجبة، وحدث «طبخناها» ثلاث معلومات منفصلة. نضيف «عايزين نجربها» وسجل آخر طبخ دون فرض وصفة كاملة.
- اختيار الوجبة لا يخصم المخزون. عند تسجيل الطبخ يمكن عرض مراجعة استهلاك اختيارية؛ تبقى الكميات المقترحة قابلة للتعديل.
- الاقتراحات تبدأ بقواعد قابلة للتفسير: الوقت، التفضيل، التنويع، استخدم أولًا، والمكونات المربوطة. الوصفة الحرة تظل صالحة ولو الربط ناقص.
- مكوّن مكتوب كنص وكمية مثل «حسب الحاجة» لا يصلح لحساب كفاية دقيقة. نضيف مرجع صنف وكمية/وحدة منظمة اختياريًا، مع الاحتفاظ بالنص القديم.
- ندعم استخدام كمية محددة، أو «قليل/خلص»، أو جرد دوري. لا نفرض تسجيل كل معلقة زيت.
- النقص ينظر للدفعات الأخرى والوحدات المتوافقة، ويقترح إعادة الشراء عند الحاجة. لا يعاد إنشاء نفس النقص عند كل تحديث أو من كل مدخل.
- الشراء الجزئي يحفظ المطلوب والمشترى والمتبقي. «اشتريت» و«أدخلت المخزون» حالتان منفصلتان، مع إجراء يجمعهما بعد مراجعة الكمية والمكان والصلاحية.
- أوامر الاستهلاك والاستلام المشتركة تحتاج هوية عملية دائمة ومعاملة خادمية حتى لا يضيع استهلاك متزامن أو تتضاعف كمية بعد إعادة إرسال.
- سياق «في السوبرماركت / عند أهلي / مستلزمات البيت» يدوي أولًا، وله قائمة واضحة غير مشتراة. الموقع التلقائي والإشعارات خارج التطبيق عمل منفصل إن احتجناه.

### المشاركة

هوية المساحة الحالية home/work تصنيف وظيفي؛ ليست هوية بيت. نضيف بيتًا بعضويات ودعوات، ونثبت إمكانية أكثر من نطاق دون تعميم صلاحيات كل النظام من أول مرحلة.

الافتراض المقترح: المطبخ وقائمة الشراء داخل البيت مشتركين بعد اختيار نقل البيانات، والمهام خاصة عند الإضافة مع خيار مشاركة واضح. هوية المنشئ، ومالك المورد، والشخص المكلف، ومن يملك الوصول، مفاهيم منفصلة. دور مدير البيت لا يمنحه قراءة مهمة خاصة تلقائيًا.

نبدأ بـ owner/editor/viewer وبمشاركة البيت، ثم نوسع لاختيار أشخاص أو أقسام عند وجود استخدام واضح. نثبت قاعدة أن العنصر الخاص لا يصبح مكشوفًا بسبب مشاركة قسمه، ولا نعرض بياناته في Today أو البحث أو الروابط أو معاينة التصدير لمن لا يملكها.

عند سحب العضوية: يرفض الخادم القراءة والكتابة اللاحقتين، وتزال النسخة النشطة والاختيارات عند اكتشاف السحب، ولا تعيد العمليات المعلقة منح الوصول. لا يمكن محو ملف سبق تصديره أو ضمان المحو من جهاز لم يتصل بعد. الاستيراد لا يمنح عضوية ولا يعيد نشر بيانات خاصة تلقائيًا.

التقويم العام وتقويم كل مساحة عرضان لنفس المصادر بفلاتر مختلفة. لا نحتاج جدول «نسخ مهام التقويم». يمكن إضافة أحداث مستقلة مستقبلًا إذا كانت غير ممثلة بمهمة. تاريخ بلا ساعة يبقى تاريخًا محليًا؛ موعد بساعة له سياسة منطقة زمنية واضحة، وأيام العمل قابلة للتحديد.

## موجز التصميم للموبايل

نحتفظ بالتنقل الحالي: الرئيسية، المطبخ، المشتريات، إدارة المنزل، ونختبره قبل إضافة تبويبات أكثر.

- الرئيسية تعرض قرارًا أو إجراءً: هناكل إيه، استخدم أولًا، نواقص، والمناسب من أعمال البيت. تفاصيل القوائم خلف «عرض الكل»؛ لا قوائم داخل مساحات تمرير ضيقة قدر الإمكان.
- المطبخ يجمع الأكلات والمخزون وخطة الوجبات مع إجراء سريع مناسب لكل قسم.
- المشتريات تبدأ بغير المشترى وتجميع مكان/نوع الشراء، وإضافة اسم سريع، والكمية والتفاصيل اختيارية.
- إدارة المنزل تعرض الجاهز والروتين والمشاريع ولاحقًا والانتظار كعروض فوق بيانات منظمة. الصيانة فلتر واضح يصل لمهمة أو مشروع.
- نموذج الإضافة يبدأ بالاسم، والخصوصية ظاهرة؛ التفاصيل الإضافية تدريجية. الأزرار المتكررة قريبة وسهلة اللمس، والتراجع متاح حيث يصح.
- كل شاشة لها فراغ أول استخدام، تحميل، فشل، عمل دون شبكة، مزامنة معلقة وتعارض. لا تعرض «مشترك الآن» لمجرد نجاح الحفظ المحلي.
- تحقق RTL، و320/390/430px، ولوحة المفاتيح، والتمرير، والوضعين، ثم استخدام فعلي على هاتفين؛ صورة سطح المكتب لا تكفي.

تصميم الشاشات يمكن أن يجري بالتوازي على العقود المعتمدة. تنفيذ حدود المشاركة يبدأ من المرحلة صفر؛ لا نؤجل اكتشاف اعتماد المزامنة على user_id إلى ما بعد بناء كل الواجهات.

## طريقة الشغل بين المساهمين

- لكل مساهم مساحة وملفات واجهتها في فرع مستقل؛ لا يعمل اثنان في نفس checkout أثناء التعديلات.
- الخدمات المشتركة، `src/types`، `src/db`، محرك Today، المكونات العامة، و`supabase/migrations` لها تغيير منسق واحد في كل مرة. ليس معناها منع المساهمة، بل مراجعة واعتماد العقد قبل اعتماد واجهة عليه.
- دوري المقترح: مراجعة تدفق الاستخدام، قواعد المجال، مصادر البيانات، تصميم الجداول والصلاحيات والترحيل، ومراجعة التكامل واختبارات القبول. لا توجد متابعة تلقائية لشغل خارج الملفات/الفروع التي تعرض للمراجعة.
- قبل كل شاشة نكتب بطاقة: هدفها، مصدرها، العمليات التي تستدعيها، شروط ظهور عناصرها في Today، الصلاحيات، حالات الفراغ والفشل، وما الذي يُرحّل من القديم.
- لا منطق شراء أو مخزون مختلف داخل كل JSX. جميع المداخل (الرئيسية/الوصفة/المخزون/Today) تستدعي نفس خدمة الأمر المناسب.
- كل تغيير بيانات يسلم معه المحلي والسحابي والطابور والتحويلات والنسخ والاستعادة. كل ترحيل له نسخة قبلية وخطة تجربة ورجوع، ولا نحذف القديم قبل التحقق من النقل.

### أول بطاقة عمل مقترحة

**العنوان:** اختيار مهام المنزل لليوم دون إدخال مخزن الأعمال كله.

**التدفق:** أحفظ «تجديد الركنة» للمراجعة؛ من Today أبحث عن «كي القميص» وأختاره؛ أزيله من اليوم فيظل موجودًا؛ أختار خطوة محددة من مشروع وأكملها مرة واحدة.

**حدود البطاقة:** عقد اختيار اليوم وهوية المصدر/الحدوث، خدمة الإضافة والإزالة والقراءة، ترحيل dayPlan الحالي، ومداخل المنزل وToday. لا إعادة تصميم جميع مساحات التطبيق ولا إدخال مشتريات مستقلة ضمن نفس البطاقة.

**القبول:** لا تتغير deadline عند الاختيار أو الإزالة؛ لا تدخل مشاريع backlog/waiting كعمل جاهز؛ لا تنسخ المهمة أو الإنجاز؛ اختيار الخطوة لا ينتقل للخطوة التالية تلقائيًا؛ الترحيل وإعادة المحاولة والمزامنة والنسخ تحفظ الاختيارات دون تكرار؛ لا تتغير بقية المساحات سلوكيًا دون قرار صريح.

## التحقق أثناء هذه المراجعة

- `npm test`: نجح، 202 سيناريو محلي. يستخدم fake-indexeddb وبدائل للشبكة؛ هذا ليس اختبار مشاركة بحسابات فعلية.
- `npm run build`: نجح TypeScript وVite وتوليد PWA. ظهر تحذير حجم الحزم؛ أكبر ملف JavaScript نحو 1.65 MB قبل gzip، فتظل سرعة التحميل على هاتف وشبكة فعلية بند تحقق عند تطوير التصميم.
- قراءة metadata للأعمدة والسياسات ودوال المزامنة فقط؛ دون تعديل SQL أو قراءة محتوى البيت.
- لم تجرِ مراجعة بصرية أو تجربة موبايل ضمن هذه المراجعة.
- التوثيق القديم يحتوي أرقام schema وحالات مزامنة تجاوزها الكود: Dexie الحالي v10، والمخزون ضمن النسخ، ومزامنة الإصدارات والحذف موجودة. يلزم توحيد المراجع في المرحلة صفر.

مرجع التفويض: [Supabase — Row Level Security](https://supabase.com/docs/guides/database/postgres/row-level-security).

## توحيد المقترحات بعد مراجعة اقتراح المساهم الآخر

هذه الإضافة تراجع النص الذي أرسله المستخدم من مساعد زميله. القرارات أدناه **توصية موحدة للنقاش**، وليست اعتمادًا للتنفيذ أو للجداول. لا ننشئ مسار تنفيذ آخر موازٍ للخطة أعلاه.

### ما نأخذه من الاقتراح

- وضع شراء للموبايل: غير المشترى أولًا، فلتر السياق، قراءة ولمس مريحان، وبقاء القائمة متاحة عند انقطاع الشبكة مع إظهار حالة التحديث.
- مدخل إضافة سريع في المنزل: فكرة أكلة، تحديث مخزون، غرض شراء، أو عمل منزلي. تظهر الحقول المناسبة للعملية فقط؛ لا نضع كل أنواع الإدخال في فورم واحد.
- إظهار «جربناها / عايزين نجربها»، مع الاحتفاظ بسجل الطبخ المستقل؛ إضافة وصفة قديمة مجربة لا تشترط اختلاق تاريخ طبخ.
- عقد خدمات واحد للواجهات، وموجز لكل شاشة، وملكية واضحة للملفات، وToday والتقويم كمراجع إلى المصادر.

### ما نعدله قبل كتابة Types أو SQL

| الاقتراح | القرار الموحد وسببه |

| inventory_item_id مرجع الصنف | السجل الحالي دفعة لها مكان وصلاحية؛ رابطها مفيد لتتبع مصدر النقص، لكنه ليس هوية عامة للصنف. نضيف تعريف صنف تدريجيًا عند الحاجة للربط بين دفعات أو وصفات، ولا ندمج دفعات قديمة بالاسم وحده. |

### دقة التشخيص

المهام غير المؤرخة والمشتريات قد تدخل أجندة Today بالفعل، لكن الظهور لا يعني أن محرك القرار يصنفها كلها إلزامية؛ يوجد فصل للأساسيات حاليًا. نصلح سياسة التجميع والعرض مع الحفاظ على هذا الفصل. كذلك لا نحذف العناصر التي تجاوزت موعدًا ثابتًا عند تطبيق فلتر «النهارده فقط»، ولا نخلط موعد المراجعة بموعد الإنجاز.

### تقسيم التنفيذ المقترح

1. نثبت عقد المهمة وخطة اليوم والنطاق والخصوصية أولًا، مع حسم مصدر إنجاز خطوة المشروع. لا ننشئ نفس الخطوة كإنجازين في projects وlife_tasks.
2. أول تسليم متكامل: اختيار عمل منزل موجود لليوم وإزالته وإنجازه من المصدر، دون إدخال المؤجل والمنتظر تلقائيًا. تبقى أول بطاقة العمل السابقة نقطة البدء.
3. بعد تثبيت العقود، يمكن العمل بالتوازي: مساهم لواجهات المطبخ والمشتريات، ومساهم لواجهات إدارة المنزل والتكامل المرئي مع Today. التقويم مهمة لاحقة مستقلة، وليس ضمن حزمة Today الأولى. عند امتلاك مساحات أخرى نستخدم نفس الحدود والعقود.
4. خدمات المشتريات وترحيلها، ثم تجربة بيت وقائمة مشتركة، ثم استهلاك/استلام مشترك وربط الأكل، ثم التكرار والتقويم، وفق بوابات القبول السابقة.
5. كل تغيير مشترك يحدد ملفات مالكه ونقطة الدمج ومعايير القبول في بطاقة قصيرة؛ لا يبدأ مساعدان بتغيير src/db أو src/types أو migrations على افتراضات مختلفة.
