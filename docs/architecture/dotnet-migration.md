# خطة فصل backend والانتقال إلى .NET

هذه خطة مقترحة، وليست API أو backend منفذًا. لا يلزم التخلي عن Supabase الآن: يمكن إبقاء Postgres وحتى Auth تدريجيًا، وبناء ASP.NET Core فوق البيانات مع نقل المسؤوليات على مراحل.

## حدود التطبيق المطلوبة

الواجهة الحالية تستدعي supabase-js من syncEngine وخدمات الحفظ وAuthContext. قبل التبديل، عرّف واجهات TypeScript مستقلة عن المزود مثل AuthGateway وSyncGateway وTaskRepository وProjectRepository. احتفظ بـDexie للتشغيل المحلي، واجعل مزود Supabase ومزود HTTP/.NET خلف نفس العقود. لا يوجد هذا الفصل مكتملًا حاليًا.

قسّم الخدمات بحسب المجال: الحسابات والتفويض، المهام، المشاريع، الخطط والمراحل، الصحة، العبادة، التخطيط اليومي، ثم المخزون والوصفات والوجبات والمشتريات عند تنفيذها. ملفات المساحات تحدد ما هو موجود وما هو مقترح لكل خدمة.

## عقد بيانات قابل للنقل

| الموضوع | القرار المطلوب |
|---|---|
| الهوية | احتفظ بمعرفات text الحالية؛ لا تجبرها كلها إلى Guid لأنها ليست بالضرورة UUID |
| صاحب البيانات | userId من الهوية الموثوقة للخادم، لا تثق بقيمة يرسلها العميل وحدها |
| المشاركة | صلاحيات مورد واضحة، خصوصية افتراضية، ومتابعة تختلف عن تعديل |
| اليوم والوقت | DateOnly للتاريخ المحلي، TimeOnly للوقت، DateTimeOffset للتوقيت الفعلي؛ احفظ المنطقة الزمنية عند الحاجة |
| null والمجهول | حافظ على الفرق بين مجهول وصفر، وبين غائب وإزالة قيمة في التحديث |
| النسخ | API version وschemaVersion للنسخ المحمولة منفصلان عن EF migrations |
| التحديث | إصدار سجل متزايد من الخادم، ومقارنة بالإصدار الذي عدله العميل |
| الحذف | tombstone أو سجل تغييرات حتى يصل الحذف للأجهزة غير المتصلة |
| إعادة الطلب | operationId فريد يجعل العملية idempotent ولا يكرر سجلًا أو وقت تركيز |

## المزامنة المقترحة

API مبدئي: GET /api/v1/sync/changes?cursor=... وPOST /api/v1/sync/mutations. الطلب يضم operationId وentityType وentityId وbaseVersion وpayload؛ الاستجابة لكل عملية applied/conflict/rejected مع الإصدار وسبب واضح. هذه أمثلة تصميم وليست مسارات موجودة في التطبيق.

المزامنة تحمل تغييرات منذ cursor من الخادم، وليس منذ ساعة جهاز العميل. حدّد pagination وتثبيت نطاق القراءة وتقدم cursor عند نجاح التطبيق محليًا. على العميل احفظ التعديل والطابور معًا في معاملة، ولا تحذف العملية قبل الإقرار بها. عند تعارض نص أو كمية جرد أو ترتيب يوم، احتفظ بالنسختين واعرض الاختيار بدل last-write-wins الصامت. وفر سياسة منفصلة للإنجازات القابلة للجمع، واختبرها قبل اعتمادها.

منع العبور بين الحسابات يبدأ محليًا: قاعدة لكل حساب أو مفاتيح userId على كل البيانات والطوابير والكاش، مع فصل بيانات الضيف ونقلها بإجراء واضح. لا ترفع قاعدة الجهاز كلها لمجرد دخول حساب جديد.

## PostgreSQL وEF Core

استخدم [لقطة الجداول الحالية](supabase-current.md) كمرجع مراجعة للأنواع والحقول، ثم استخرج schema dump كاملًا قبل النقل الحقيقي، بما يشمل القيود والمنح والفهارس والدوال والـtriggers والسياسات ذات الصلة. ملفات MD لا تعيد إنشاء قاعدة كاملة.

أنشئ migrations قابلة للمراجعة تحت إدارة الإصدارات. قاعدة auth.users وJWT الخاصة بـSupabase ليست جدول مستخدمين يمكن نسخه ببساطة إلى ASP.NET Identity؛ إما إبقاء Auth مؤقتًا والتحقق من توكناته، أو تصميم نقل هويات وإعادة دخول وربط معرفات دون مطالبة المستخدم بتصدير كلمات المرور. لا تنقل مفاتيح service_role إلى المتصفح.

إلغاء RLS عند الانتقال دون بديل تفويض خادمي يغيّر نموذج الأمان؛ حدّد هل ستحتفظ بها أم تطبق الملكية والمشاركة عبر الخدمات وقاعدة البيانات معًا. اختبر سياسات القراءة والإضافة والتعديل والحذف بحسابين قبل التبديل.

## ترتيب النقل والتحقق

1. تثبيت التوثيق وعمل نسخة بيانات وschema مستقلة قابلة للاستعادة.
2. إصلاح عزل الحسابات والمزامنة الحالية ومعالجة الأخطاء وتوحيد mappers؛ استكمال الجداول الناقصة بمigrations منفصلة.
3. تعريف عقد API واختبارات مشتركة لمزودي Supabase و.NET.
4. نقل مجال واحد على بيئة اختبار مع الحفاظ على المعرفات والروابط، ثم مقارنة عدد السجلات والقيم والإنجازات.
5. تجربة جهازين: تعديل دون شبكة، إعادة اتصال، إعادة نفس الطلب، حذف، تعارض، تبديل حساب، ومشاركة بصلاحية عرض فقط.
6. تبديل المزود مع إيقاف الكتابة للمزود القديم خلال النقل النهائي؛ تجنب dual-write غير المنضبط. احتفظ بخطة رجوع ونسخة قبل التبديل.

اختبارات القبول تشمل استيراد JSON قديم، واستعادة بعد فشل كتابة، وعدم فقد الحقول المحلية الغائبة عن Supabase الحالي. نقل backend لا يصلح هذه الفجوات تلقائيًا. لا تصدّق نجاح الواجهة فقط؛ قارن البيانات من جهازين تحت صلاحيات المستخدمين الفعلية.
